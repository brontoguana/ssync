# SSync implementation plan

Native version 4.0.0; Java reference version 3.3. Native local install/update/uninstall supersede the earlier self-install exclusion. Revised after user decisions — 2026-10-12. Native implementation has not started. Authentication library/profile and remaining behavior details still need selection.

## Scope and recommendation

Confirmed requirement: the native executable transfers files only. Do not implement script hooks, remote commands, shell expansion, subprocess launching, executable configuration, or remote management command execution. Unknown options and unsupported protocol operations fail explicitly.

Confirmed: drop Java wire/network compatibility and use a new versioned protocol. Preserve actual usage and commands largely unchanged: the CLI, configuration, and transfer workflows are an API. Both endpoints must use the native tool; fail clearly when contacted by a Java protocol-6 peer. Recommend Rust. Reject script/command execution options explicitly.

### CLI/API compatibility contract

- Preserve `ssync [qualifiers] <action> <location> [files or folders]`, including `put`/`get` once and `offer`/`accept` continuously. Preserve independence between transfer direction and TCP connection direction.
- Preserve numeric listener ports, listener aliases, `host:port` / `host:alias`, and the existing Java alias-to-port mapping. The alias mapping is a user-facing contract even though the wire format changes.
- Preserve `SSYNC_PASSWORD` precedence, `password@location`, hidden password prompts, and generated listener passwords. Add safer secret-file/input-descriptor alternatives without requiring them or removing existing invocation syntax. Inline passwords may appear in process listings/history; redact them from SSync logs and errors.
- Preserve transfer qualifiers and parsing: `merge`, `nodelete`, `dryrun`, `verify`, `verbose`, `force` / `noprompt`, and substring `skip:` filters. `force` / `noprompt` do not bypass password policy, root authorization, or protocol validation.
- Preserve `.ssync` files as declarative lists of allowed internal transfer operations, including concurrent operation where safe; never interpret them through a shell or execute arbitrary commands. Preserve `?` guidance and file-inspection/version commands. Specify `hash` / `deep` output expectations before replacing their algorithms.
- Add `ssync pwd`: print exactly one freshly generated password followed by a newline to stdout, then exit successfully. Use the same generator as automatic listener passwords. No labels, progress messages, connection, transfer, or filesystem side effects. Report generation failure on stderr with a nonzero exit code.
- Preserve operator-selected path behavior, including documented current-directory defaults when arguments are omitted; resolve and display that local root. The remote peer cannot select a broader root. Do not require new path arguments without an explicitly documented API decision.
- Inventory and test legacy parsing, prompts, filters, overwrite/deletion defaults, diagnostic commands, and exit behavior before implementation. Changes such as deletion-off by default or stronger `verify` semantics remain proposals, not implied user approval. Failures must report nonzero exit status rather than reproduce legacy false-success bugs.
- Intentional changes: new incompatible wire protocol, strict rejection of execution features (including remote management), confirmed minimum password length, and explicit errors for unsupported operations. Record all deviations in a migration guide.

Rust produces platform executables without a separately installed language runtime. Supported operating systems and architectures must be selected before the release matrix is finalized; propose Linux/macOS amd64/arm64 initially and make Windows an explicit scope decision.

## Password assessment from the supplied source

`SSync.newPassword()` concatenates Base58 encodings of two random positive longs, keeps the first 16 characters, and inserts hyphens every four characters. `AbstractBCUtil.getNextAbsID()` uses Java SecureRandom, rejects Long.MIN_VALUE, and takes the absolute value. The output resembles four groups of four Base58 characters.

Sixteen uniformly independent Base58 characters would represent about 93.7 bits (16 * log2(58)). This generator is not uniform over that space: separate positive-long encoding and prefix truncation create a different distribution. Do not repeat the source's exact 93-bit estimate or its time-to-crack comments as established facts. The generated random secret appears amply strong for short-lived transfers under the inspected SRP design; this is a source assessment, not a cryptographic audit. User-chosen passwords can have far less entropy despite comparable length.

The supplied SRP code uses random salt/ephemeral secrets and mutual proofs. Its password transformation uses SHA-256 rather than a memory-hard KDF. The continuous listener already implements per-IP throttling after five failures, with exponential cooldown from five to sixty seconds, 120-second socket timeouts, and a bounded worker pool/queue. The throttle is in memory and is not a global or per-credential budget; one-shot paths do not use that listener throttle. These observations describe supplied protocol-6 source, not all deployed Java builds.

## Proposed authentication and transport

### Password format and lifetime

Confirmed: support reusable passwords for long-running and repeated syncs. No automatic password expiry, forced periodic rotation, or invalidation on successful transfer. One-shot mode ends its listener after a transfer; it does not destroy or invalidate a password used in another invocation. Rotation or revocation is operator-controlled. Handshake timeouts and bounded idle/resource policies are separate from credential lifetime and must not cap the total duration of a progressing transfer.

Confirmed: generate 24 independently uniform Base58 characters with the OS cryptographic random generator and display them as six groups of four separated by hyphens. Use this format both for automatic listener passwords and `ssync pwd`. Use the existing alphabet `123456789ABCDEFGHJKLMNPQRSTUVWXYZabcdefghijkmnopqrstuvwxyz`, which excludes `0`, `O`, `I`, and `l`. Base58 remains case-sensitive. Use unbiased sampling (e.g. rejection sampling), not byte-modulo-58, truncated integer encodings, or a noncryptographic PRNG. This yields approximately 140.6 bits of randomness; grouping adds none. Preserve entered passwords exactly, including hyphens; do not silently strip separators, fold case, trim, or truncate user-supplied credentials. If an ungrouped input alternative is later desired, specify it as a separate generated-password format rather than changing arbitrary password semantics.

Base32 offers 5 bits per independent character and can use a case-insensitive transcription format. Base58 offers log2(58), approximately 5.858 bits per independent character. Encoding 128 random bits needs at most 26 Base32 or 22 Base58 characters; encoding cannot add entropy. Sampling 22 uniform Base58 characters instead gives about 128.9 bits. The confirmed 24-character Base58 generator gives extra margin for persistent credentials while remaining compact and readable. Its displayed length is 29 characters including the five hyphens.

Confirmed: accept supplied passwords of at least 16 Unicode code points; reject shorter passwords. Apply this minimum locally before opening a listener or starting a connection, consistently across prompts, environment, inline syntax, and `.ssync` configuration. Permit long passphrases (at least 64 characters); define an explicit generous byte limit for resource safety and reject oversize input without truncating. Separately proposed, not yet accepted: reject locally known common/compromised full passwords and obvious weak values using a bundled, offline policy; never send the secret to a remote password-check service. Avoid arbitrary uppercase/digit/symbol composition rules. Length alone does not establish entropy: a predictable 24-character phrase can be weaker than a random 16-character secret. Existing random 16-character passwords remain usable; shorter legacy passwords intentionally fail with a clear explanation. The 16-character minimum and 24-character generator are accepted; any additional blocklist/pattern policy remains a proposal.

### Password-only authenticated channel

Recommend an established password-authenticated key exchange (PAKE) with mutual key confirmation, fresh ephemeral keys per connection, and an established authenticated-encryption transport. Keep the existing endpoint-plus-password UX; do not require a fingerprint/pairing ticket for ordinary transfers. Passive capture must not allow an offline password-guessing test, and active wrong-password attempts must fail before metadata or filesystem access. Bind version negotiation, peer roles, transfer direction, and the authorized operation to the authenticated session, using the chosen protocol's reviewed mechanisms. No custom recreation of the Java SRP or encryption framing and no password-derived static traffic keys.

Select a maintained implementation and a documented complete channel construction before writing transfer code. Balanced PAKE profiles suit peers independently provisioned with the same password; OPAQUE is an augmented PAKE with a registration model and is not automatically a drop-in here. Evaluate memory-hard password processing where supported by the selected profile, with specified salts, bounded/calibrated parameters, and resistance to attacker-selected KDF resource costs. Do not bolt an unreviewed PAKE onto TLS or invent key schedules. TLS with authenticated certificates/pins and password authentication remains an alternative only if it can preserve the agreed workflow; sending a password to an unverified self-signed TLS endpoint is unacceptable.

A PAKE mitigates capture-based offline guessing, not all guessing or compromise: online guesses still need limits, and compromise of stored passwords/verifiers or an authorized endpoint has different consequences. A holder of a reused password can authenticate for its configured scope until the operator changes/revokes it. Generate independent session keys regardless of password reuse and choose a construction with forward secrecy.

### Brute-force and resource controls

Apply per-IP, per-credential (where identifiable before successful authentication), and listener-wide admission/failure budgets to every listening mode, including protection against attempts spread across IPs. Use bounded expiring state and increasing temporary delays; never let unauthenticated failures permanently invalidate a credential or disconnect an established transfer. Specify restart behavior rather than relying on in-memory limits as permanent protection. Test concurrency, changing IPs, IPv6, NAT, listener restart, and incomplete handshakes.

Bound unauthenticated sessions, handshake duration, expensive KDF concurrency, frame/allocation sizes, file counts, pending partial data, and logging. Keep throttling outside expensive work where possible; do not disclose password validity through distinguishable error detail or timing beyond unavoidable admission behavior. Rate limiting reduces guess rate and resource abuse, but cannot guarantee availability against flooding. Long-term protection rests primarily on high-entropy secrets and an appropriate authenticated protocol, not scheduled expiry.

### Explicit password confirmation

Confirmed: validate the password thoroughly on every connection. Use the chosen established protocol's explicit mutual key-confirmation mechanism: each peer must verify proof that the other derived the same fresh session key, bound to that handshake and its roles/context. Never send the password or a static password hash as a check, and never treat successful TCP connection or decrypted-looking bytes as authentication. The supplied Java SRP already has mutual M1/M2 proofs; preserve this property and strengthen state-machine enforcement and coverage rather than claim it is missing.

A peer stays unauthenticated until it verifies the required proof; it cannot list filenames, inspect transfer roots, allocate transfer partials, overwrite, delete, or start the transfer engine before authentication completes. Credential loading/policy validation is local; it is separate from proving the remote password matches. Use library constant-time comparisons where appropriate, clear failure/nonzero exit status, and bounded rejection handling. Test one-character substitutions, wrong case, missing group separators, minimum-length inputs, long inputs, malformed/truncated proofs, stale proofs from an earlier connection, role reflection, altered negotiation, timeout/cancel during confirmation, and reconnect with the same password but independent session keys. Operator-supplied secrets are preserved exactly. A failure must disclose no file metadata and leave both roots unchanged. Extra ad hoc password challenges are not a substitute for a reviewed construction.

## Required efficient transfer behavior

Confirmed: retain the efficient transfer method. The Java `FileMirror` uses fixed 200,000-byte blocks, concurrent metadata/hash comparison and data streaming, skips matching blocks, and sends differing or missing blocks with offsets and final file length. It skips whole files found unchanged. This is fixed-block delta transfer, not rsync rolling checksums. Preserve 200,000-byte blocks as the initial native default and preserve overlapping comparison/transfer with bounded queues and backpressure; do not turn incremental sync into whole-file retransmission. Replacing MD5 and the codec is permitted by the wire-compatibility break; select a modern content hash and verify the complete reconstructed file before committing it.

For safe updates, create a private staged file, reuse verified unchanged ranges from the existing destination, apply changed ranges, truncate to the authenticated final size, validate the final hash, and atomically replace that individual file. This can add local disk I/O compared with in-place Java writes; measure it separately from bytes transferred on the network. Bound manifests/queued hashes for large files instead of copying the Java per-file in-memory hash arrays. Detect source mutation and conflicting destination changes so a reconstructed mixture never reports success. Interrupted-transfer resume must validate retained ranges before reuse. Identical files must send zero file-content bytes; fixed-block insertion can invalidate later blocks and is not promised to have rolling-checksum efficiency.

Release tests must measure file-content bytes, protocol/metadata bytes, local read/write bytes where available, peak memory, and elapsed time separately. Exercise a 20,000,000-byte deterministic/random fixture: initial copy, identical repeat, one byte changed inside one block, separated changed blocks, append, shrink, same-size/same-mtime corruption, interrupted restart, and source mutation. A one-block change must send one changed block's payload (at most 200,000 bytes), plus authenticated metadata/hashes, rather than the entire file. Correctness and final hashes are mandatory alongside bandwidth results. These are required release gates, not optional future optimization.

## File-only security boundary

- The local operator selects source/destination roots and upload/download/overwrite/delete permissions. A remote peer cannot expand them. Resolve roots from local CLI/configuration, including preserved documented current-directory defaults, and show them clearly. Never expose additional roots based on a remote request.
- Permit ordinary files and directories only initially. Reject absolute paths, parent traversal, symlinks, hard-link creation, devices, FIFOs, sockets, invalid platform paths, duplicates, case collisions, and unsupported metadata. Reject or safely handle existing destination hard links and mount/reparse boundaries.
- Enforce containment through directory-relative, no-follow filesystem operations and platform equivalents. A canonical-path string prefix check is insufficient against concurrent symlink/reparse changes. If equivalent guarantees are unavailable on a target, fail safely or defer that target.
- Do not honor remote executable/setuid bits, ownership, ACLs, or executable hooks. Keep restrictive receiver-selected file modes. Files may contain any bytes, including programs, but SSync never executes them. Writing into a startup/script/config directory can still have effects through other software; the chosen root and OS permissions remain part of the trust boundary.
- Overwrite/deletion policies are set locally and scoped to the destination root. Preserve `nodelete` and `dryrun`; specify default behavior in the CLI contract before implementation. Deletion-off by default is a proposed safety change needing an explicit API decision. Any enabled deletion occurs only after a complete verified transfer; dry run previews changes without writing transfer state.
- Transfer into private temporary files on the destination filesystem, verify content, then atomically rename each completed file. Preserve existing files on failed updates. Define cleanup/retention of partials and sync-to-disk durability; do not claim an entire directory tree is atomically committed.
- Treat filenames as data and escape terminal control characters in output. No subprocess-based transfer helpers or shell-based path handling.

## Implementation stages and completion gates

1. Freeze CLI, capabilities, connection/transfer directions, authentication UX, overwrite/delete/filter semantics, supported platforms, and stable exit codes. Record the confirmed wire break and the CLI/API compatibility matrix, with all intentional deviations. Write the versioned message/state specification and threat model.
2. Prototype only connection/authentication: select maintained Rust libraries and a documented PAKE/channel profile; exercise password policy, mutual confirmation, rejection, deadlines, concurrent attempts, reusable credentials, and rate-limit budgets. Verify authentication binds session, root, and direction. Gate: no unauthenticated metadata or filesystem access, no offline-guessing transcript, no unverified-password endpoint, and no credential expiry during long-running/repeated syncs.
3. Implement safe full transfers: regular files/directories, streaming bounded memory, Unicode/empty/large files, local permission checks, content hashes using SHA-256 or BLAKE3, per-file atomic replacement, truthful errors, and cleanup. Gate: malicious peers cannot escape roots or request execution; failed transfers do not destroy existing files.
4. Implement the required efficient synchronization engine: preserve fixed 200,000-byte block comparison, overlapping metadata/data streaming, whole-file and matching-block skips, offset-based changed-block transfer, and safe resume. Use authenticated manifests and verified final hashes. Full-copy scaffolding from stage 3 is not a releasable replacement for the efficient Java method; bandwidth/memory regression gates are mandatory. Bind partial state to credential/root/file identity; detect concurrent source changes. Implement the agreed CLI deletion/dry-run/filter policy. Gate: deltas and resumes produce the same verified content as full transfers, and deletion never proceeds from an incomplete/unverified manifest.
5. Add continuous offer/accept service behavior: scoped credentials, bounded concurrency, destination locking, operator-controlled rotation/revocation without automatic expiry, graceful cancellation, signal cleanup, clear progress/logs, and restart behavior. Gate: conflicts fail clearly, partials remain bounded, and a failed transfer cannot report success.
6. Validate and release: integration tests between native peers in every supported transfer/connection direction; malformed-message fuzzing; tampering, replay, wrong passwords, reused credentials, long-running transfers, operator revocation, path/link races, disk-full, permissions, disconnects, conflicting writers, source mutation, and platform tests. Add CLI/configuration fixtures based on the Java reference; Java/native wire interoperation and old crypto vectors are explicitly not release gates. Create the separate public repository and regular commit/push/build workflow, platform archives, verified installer, checksums, and signing/verification design. Inspect imported source redistribution terms before public upload; keep reference archives/dependencies out of public history unless cleared.

Release runtime contains no Java, Python, shell, or reference-JAR dependency. Developer build/test tooling may use scripts. Reference material remains unchanged and separate from native production code.

## Complexity and decisions still open

Confirmed: new wire protocol; CLI/configuration/workflows are an API and must largely remain the same; strict file-only operation; reusable passwords without automatic expiry; minimum 16-character supplied passwords; 24 random Base58 characters displayed in six groups of four for generated passwords; `ssync pwd` prints one such password. Dropping Java wire compatibility substantially reduces codec, custom crypto, legacy MAC, Java numeric/string framing, and interoperability work. CLI/alias/configuration compatibility remains real work. Safe filesystem access, authenticated channels, deltas/resume, and concurrent lifecycle management still make this a substantive project; no calendar estimate is established.

Recommendations: Rust, a separately proposed local weak-password blocklist, password-only PAKE authentication, and standard authenticated encryption. Ready to begin implementation with CLI/password generation and authentication evaluation as the first milestone. Select and validate the authentication construction before adding transfer traffic. Still to settle during implementation: final PAKE/channel library/profile, any additional weak-password policy, exact intentional CLI deviations (including deletion defaults and hash outputs), overwrite semantics, Windows scope, and detailed resume-state retention policy. Fixed-block delta efficiency is confirmed scope, not an open priority decision. Continuous/repeated use is required and must be included in design and validation from the start. No native implementation or publication was performed in this planning pass.

## Isolated validation lab

Confirmed authorization: create up to two Podman peers for actual transfer, encryption, feature, and file-safety testing. `tests/podman/lab.py` creates two rootless nonprivileged peers on a dedicated internal network, with no host bind mounts, no published ports, read-only root filesystems, dropped capabilities, bounded resources, and disposable tmpfs storage. See `tests/podman/README.md` for commands, constraints, and `tests/TEST_MATRIX.md` for the release matrix. Future test harnesses and native binaries are copied into the peers, not given writable access to this checkout or other host directories. Use container-local outside-root canaries for adversarial path/deletion tests. No privileged containers or host networking/device exposure.

The lab connectivity smoke is only an infrastructure check. It does not prove SSync authentication, encryption, delta transfers, or file containment before native implementation exists. Record exact binary versions, commands, settings, outcome and raw evidence under ignored `target/` and `DEBUGLOG.md`, with public reproducible test procedures in the repository. Tests marked planned are required before release, not reported as passing.
